When should an encrypted classifier add rotation keys?

We tested a client that starts ConvMNIST with 17 rotation keys. When a sixth request arrives, it uploads rotation keys for +512 and +2048, waits for both acknowledgements and answers with 19 keys.

On the prespecified session mix, this rule was 12.5 ms faster than Fixed 19 when public keys were prepared. With keys generated on demand, it was 101.3 ms faster than Fixed 19 in a smaller follow-up.

The primary difference has an exploratory 95% paired bootstrap interval of -28.3 to +5.8 ms for switching minus the fastest fixed choice, reselected in each resample. The data support a conditional recovery point for a client already using 17 keys. A general enrollment-time advantage needs a separate deployment replication.

How the workload changes the result

The independent sensitivity uses the published lengths of 199,036 human conversations with vision-language models. Only 3,941 (1.98%) reached a sixth turn. We counted each conversation once and capped 114 conversations at 24. Applying their length distribution to the encrypted measurements tests how the result changes for a different workload. The two sequential key installations each require one extra round trip in sessions that reach prediction six. A simple sensitivity adds 0.4 times any extra round-trip latency to the mean adaptive penalty on the designed mix. An additional 50 ms per round trip therefore shifts that comparison by 20 ms. This calculation assumes all other transport and compute costs stay fixed.

What was verified

The primary cohort ran 1,152 encrypted predictions, 48 setups and 24 live key updates, with 0 class disagreements against scalar inference and the test labels. The separate on-demand cohort ran 384 encrypted predictions. Each session cycled through the same eight MNIST test images, with fresh ciphertexts at each request position. All four arms appeared equally often in each run position.

Both processes ran on one Apple M5 Pro. The sender paced upload frames to 500 decimal Mbit/s on local TCP, with unpaced replies. Each evaluator used one thread. The evidence kit includes a two-host runner, raw receipts, frozen protocol and replay checks. A separate local integration check sent four real encrypted predictions, including both additions, through the runner using loopback forwards and a mock SSH executable. It verifies the code path on this host.

These results describe the completed single-machine experiment. The repository records the subsequent two-Mac replication in a separate partial checkpoint.
